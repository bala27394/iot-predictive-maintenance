# Dashboard Walkthrough: IoT Predictive Maintenance Command Center

This document explains what each of the 7 navigation views in the Streamlit dashboard shows, what data powers it, what each table and chart means, and how a maintenance team would use it in practice.

---

## How the Dashboard Works

The sidebar on the left has 7 navigation options. Each one is a different view of the factory floor, designed for a specific question a maintenance manager, plant engineer, or technician would ask during their day. The dashboard reads live from Snowflake dynamic tables and analytics tables -- the data refreshes automatically as the pipeline runs.

---

## View 1: Factory Floor Overview

**What it answers:** "At a glance, how is my entire factory doing right now?"

This is the landing page. It gives the plant manager a single-screen summary of all 50 machines.

**KPI Cards (top row):**

| Card | What it shows |
|------|--------------|
| Total Machines | Count of all machines being monitored (50) |
| Critical | How many machines are in CRITICAL health status (score below 40) -- these need immediate attention |
| Warning | Machines showing early signs of trouble (score 40-60) |
| Avg Health Score | The fleet-wide average health score out of 100 -- a quick pulse on overall factory health |

**Machine Health Scores Table:**

This table lists every machine on the factory floor, sorted worst-first. Each row is one machine.

| Column | What it means |
|--------|--------------|
| MACHINE_ID | The unique identifier for the machine (MCH-0001 through MCH-0050) |
| MACHINE_TYPE | What kind of machine it is -- CNC_LATHE, HYDRAULIC_PRESS, CONVEYOR, INJECTION_MOLDER, PUMP, or COMPRESSOR |
| HEALTH_SCORE | A composite score from 0 to 100 calculated from sensor Z-scores, anomaly counts, threshold breaches, and signal variability. Lower means worse. |
| HEALTH_STATUS | Color-coded bucket: CRITICAL (red, below 40), WARNING (orange, 40-60), FAIR (yellow, 60-80), GOOD (green, above 80) |
| TOTAL_ANOMALIES_24H | How many anomalous sensor readings were detected for this machine in the last 24 hours |
| MOST_CONCERNING_SENSOR | Which sensor type (VIBRATION, TEMPERATURE, CURRENT, etc.) is showing the most abnormal behavior right now |
| CONCERN_RANK | Rank across all 50 machines -- rank 1 is the most concerning machine on the floor |

**How a manager uses this:** Open the dashboard at the start of the day. If any machines are red (CRITICAL), click into the Machine Detail view for those machines. If the average health score is dropping week over week, it signals a systemic issue (aging fleet, environmental stress, etc.).

## View 2: Machine Detail

**What it answers:** "What exactly is going on with this specific machine?"

This is the deep-dive view. Select any machine from the dropdown to see its full diagnostic picture.

**Machine Info Cards (top row):**

| Card | What it shows |
|------|--------------|
| Machine Type | The category of machine (e.g., CNC_LATHE, PUMP) |
| Health Score | Current composite health score for this specific machine |
| Status | Current health status (CRITICAL / WARNING / FAIR / GOOD) |

**Recent Sensor Readings (Vibration) -- Line Chart:**

A time-series line chart showing the last 200 vibration readings for this machine. The data comes from `SENSOR_READINGS_CLEAN`, which has already been null-imputed and normalized. For a healthy machine, this line is flat with minor noise. For a degrading machine, you see a clear upward trend -- vibration increases as bearings wear, shafts misalign, or components loosen.

**Why vibration?** Vibration is the single best early indicator of mechanical failure. It changes before temperature rises, before current draw spikes, and before operators can hear or feel anything wrong.

**Detected Anomalies Table:**

Lists the ML-detected anomalies for this machine, most recent first.

| Column | What it means |
|--------|--------------|
| READING_TIMESTAMP | When the anomalous reading occurred |
| SEVERITY | How bad the anomaly is: CRITICAL, HIGH, MEDIUM, or LOW -- classified by a combination of health score and ML confidence |
| SENSOR_VALUE | The actual vibration reading that triggered the anomaly |
| ANOMALY_SCORE | The ML model's confidence that this is a real anomaly (0 to 1, where 0.99+ is high confidence) |
| HEALTH_STATUS | The machine's overall health status at the time of this anomaly |

**Vibration Forecast (14 days) -- Line Chart:**

A forward-looking prediction chart generated by the Snowflake ML Forecast model. It shows where vibration is heading over the next 14 days with 95% confidence intervals (upper and lower bounds). For a healthy machine, the forecast is flat. For a degrading machine, the forecast shows an upward curve -- this is the "time-to-failure" indicator.

**How a technician uses this:** After seeing a CRITICAL machine on the Factory Floor view, they come here to understand the failure pattern. The vibration chart shows when degradation started. The anomaly table shows how frequently anomalies are firing. The forecast tells them how much time they have before the machine likely fails. This information goes directly into maintenance scheduling decisions.

## View 3: Anomaly Feed

**What it answers:** "What anomalies are happening right now, and which ones need action?"

This is the alert triage view -- the real-time feed of ML-detected anomalies across the entire factory.

**Severity Filter (top):**

A multi-select filter defaulting to CRITICAL and HIGH. Users can expand to include MEDIUM and LOW if they want the full picture, or narrow to just CRITICAL for urgent triage.

**KPI Cards:**

| Card | What it shows |
|------|--------------|
| Total Shown | Count of anomalies matching the current filter |
| Critical | Count of CRITICAL severity anomalies in the current view |
| High | Count of HIGH severity anomalies in the current view |

**Anomaly Table:**

Each row is one detected anomaly event.

| Column | What it means |
|--------|--------------|
| MACHINE_ID | Which machine triggered the anomaly |
| MACHINE_TYPE | The machine category |
| READING_TIMESTAMP | Exact time the anomalous reading was captured |
| SEVERITY | CRITICAL / HIGH / MEDIUM / LOW -- determined by a combination of health score thresholds and ML anomaly confidence |
| SENSOR_VALUE | The vibration reading that was flagged |
| ANOMALY_SCORE | ML confidence score (0 to 1). Above 0.99 means the model is very confident this is abnormal. |
| HEALTH_SCORE | The machine's overall health score at detection time |
| HEALTH_STATUS | Machine health bucket at detection time |
| OPERATOR_OBSERVATION | What the nearest shift operator reported for this machine around the same time (VIBRATION, NOISE, SMELL, LEAK, VISUAL, or null if no observation) |
| PERFORMANCE_STATUS | Whether production quality was HEALTHY, WARNING, or DEGRADED during the same shift |
| STATUS | Processing status -- NEW (just detected) or TRIAGED (already processed by the orchestration pipeline) |

**How the maintenance lead uses this:** This is the morning triage screen. Sort by severity, look at the CRITICAL items first. The OPERATOR_OBSERVATION column is the bridge between OT data (sensor readings) and human context (what the operator saw). If the ML says anomaly and the operator reported "burning smell," that corroboration raises the urgency. If the ML flags something but the operator saw nothing, it may be a transient spike worth monitoring.

## View 4: Work Order Management

**What it answers:** "What maintenance work has been ordered, and what needs to happen?"

This view shows the AI-generated work orders produced by the orchestration pipeline.

**KPI Cards:**

| Card | What it shows |
|------|--------------|
| Total Orders | Total work orders in the system |
| Critical | Work orders with CRITICAL priority -- these represent machines at imminent risk of failure |
| Assigned | Work orders that have been dispatched to a technician (status = ASSIGNED) |
| Rental Needed | Work orders where the AI recommended renting a backup machine to maintain production continuity |

**Work Order Summary Table:**

| Column | What it means |
|--------|--------------|
| WORK_ORDER_ID | Unique identifier (WO-...) |
| MACHINE_ID | Which machine the work order is for |
| STATUS | DRAFT (just created), ASSIGNED (dispatched to technician), IN_PROGRESS, or RESOLVED |
| PRIORITY | CRITICAL or HIGH -- maps to the anomaly severity that triggered the work order |
| TITLE | AI-generated short description, e.g., "Conveyor MCH-0003 Vibration Anomaly - Critical Health Score 39/100" |
| ASSIGNED_TECHNICIAN_ID | Which technician was assigned (TECH-001 through TECH-010) |
| ESTIMATED_DOWNTIME_HOURS | AI-estimated repair time: 8 hours for CRITICAL, 4 hours for HIGH |
| RENTAL_RECOMMENDED | TRUE if a backup rental machine should be arranged to keep production running |
| CREATED_AT | When the work order was generated |

**Work Order Detail Section:**

Select any work order from the dropdown to see its full AI-generated content:

- **Title:** A concise description of the issue
- **Problem Description:** A 3-sentence synthesis written by llama3.1-70b that combines sensor data, operator observations, production impact, and maintenance history into a coherent narrative. Example: "Machine MCH-0047 (PUMP) is experiencing critical issues, with a health score of 37.7 indicating potential impending failure. Operator reported burnt smell near the unit. Production reject rate has risen to 19.6% with cycle time deviation of 4.1%."
- **Recommended Actions:** A numbered 4-step maintenance checklist generated by AI, tailored to the specific machine type and failure pattern.

**How the maintenance planner uses this:** This replaces the manual process of reading sensor alerts, pulling up ERP history, calling the operator, and writing a work order from scratch. The AI has already done all of that. The planner reviews the draft, adjusts if needed, and approves.

## View 5: Maintenance History

**What it answers:** "What has failed before, and what did it cost us?"

This is the ERP context view -- historical failure records that inform root cause analysis and future predictions.

**KPI Cards:**

| Card | What it shows |
|------|--------------|
| Total Failures | Count of all historical failure events across the fleet |
| Avg Downtime (hrs) | Average repair duration in hours across all past failures |
| Total Cost | Cumulative cost of all past failures in USD |

**Machine Filter:** A dropdown to filter the history table to a specific machine, or view all machines.

**Maintenance History Table:**

| Column | What it means |
|--------|--------------|
| MACHINE_ID | Which machine failed |
| FAILURE_DATE | When the failure occurred |
| FAILURE_TYPE | Category of failure: BEARING_FAILURE, SERVO_MOTOR_BURNOUT, SEAL_DEGRADATION, HYDRAULIC_LEAK, etc. |
| ROOT_CAUSE | What caused the failure (wear and degradation, overload, contamination, etc.) |
| RESOLUTION | What was done to fix it |
| PARTS_REPLACED | Which parts were swapped out during repair |
| DOWNTIME_HOURS | How long the machine was down |
| COST_USD | Total cost of the repair (parts + labor) |
| TECHNICIAN_ID | Who performed the repair |

**How a reliability engineer uses this:** When a new anomaly is detected on MCH-0025 (CNC_LATHE), the engineer checks this view: "Has this machine failed before? What was the failure type? What parts were needed last time?" This historical context is also what the AI uses when drafting work orders -- it references past failures to suggest likely root causes.

## View 6: Business Continuity

**What it answers:** "If a machine goes down, how do we keep production running?"

This view bridges predictive maintenance with production planning. When a machine needs repair, the factory needs to know: Can we rent a replacement? Are the right parts in stock?

**Rental Machine Availability Table:**

| Column | What it means |
|--------|--------------|
| MACHINE_TYPE | Which type of machine the rental can replace |
| VENDOR | Rental company name |
| DAILY_COST_USD | Cost per day to rent |
| WEEKLY_COST_USD | Cost per week (typically 5x daily) |
| AVAILABILITY | AVAILABLE (ready to ship) or LIMITED (may have lead time) |
| LEAD_TIME_DAYS | How many days from order to delivery |
| CAPACITY_PERCENT | What percentage of the original machine's output the rental can handle |
| LOCATION | Where the rental machine is located |

**Critical Machines Needing Backup Table:**

Joins the health scores with active work orders to show which CRITICAL machines have maintenance planned and whether a rental was recommended.

| Column | What it means |
|--------|--------------|
| MACHINE_ID | The critical machine |
| MACHINE_TYPE | Machine category |
| HEALTH_SCORE | Current health score |
| HEALTH_STATUS | Should be CRITICAL for all rows in this table |
| ESTIMATED_DOWNTIME_HOURS | How long the repair will take (from the work order) |
| RENTAL_RECOMMENDED | Whether the AI flagged this machine as needing a backup |

**Parts Inventory Table:**

| Column | What it means |
|--------|--------------|
| PART_NAME | Spare part name (Bearing kit, Seal kit, Filter, Motor, etc.) |
| PART_CATEGORY | Category grouping |
| QUANTITY_IN_STOCK | How many units are currently available |
| REORDER_LEVEL | The threshold below which a reorder should be triggered |
| LEAD_TIME_DAYS | How many days it takes to get new parts from the supplier |
| UNIT_COST_USD | Cost per unit |

**How the operations manager uses this:** Before authorizing a maintenance shutdown, they check: "Is the right rental machine available? How much will it cost? Do we have the parts in stock, or do we need to expedite an order?" This view turns maintenance decisions into informed business decisions.

## View 7: Cross-Machine Health

**What it answers:** "While we have this machine down for repair, what else should we fix?"

This is the opportunistic maintenance view. When a machine is already shut down and a technician is on site, it is the cheapest time to inspect and repair nearby or related machines. This view identifies those opportunities.

**Health Score Distribution -- Bar Chart:**

A bar chart showing the health score of all 50 machines, sorted from lowest to highest. Visually, you can immediately see how many machines are in the danger zone (left side of the chart) versus healthy (right side).

**Machines by Status -- KPI Cards:**

| Card | What it shows |
|------|--------------|
| Critical | Count of machines with health score below 40 |
| Warning | Count of machines scoring 40-60 |
| Fair | Count of machines scoring 60-80 |
| Good | Count of machines scoring above 80 |

**Machines Needing Attention (Score < 70) Table:**

Filters to all machines below a health score of 70 -- the ones that should be inspected during the next available maintenance window.

| Column | What it means |
|--------|--------------|
| MACHINE_ID | Machine identifier |
| MACHINE_TYPE | Machine category |
| HEALTH_SCORE | Current composite health score |
| HEALTH_STATUS | CRITICAL, WARNING, or FAIR |
| TOTAL_ANOMALIES_24H | Recent anomaly count |
| TOTAL_BREACHES_24H | Recent threshold breach count |
| MOST_CONCERNING_SENSOR | The sensor showing the most abnormal behavior |
| CONCERN_RANK | Priority ranking across the fleet (1 = most urgent) |

**Production Impact by Machine Type Table:**

Aggregates production quality data by machine type to show which categories of machines are causing the most production issues.

| Column | What it means |
|--------|--------------|
| MACHINE_TYPE | The machine category |
| AVG_REJECT_RATE | Average percentage of parts rejected across all machines of this type |
| AVG_CYCLE_DEVIATION | Average deviation from the 7-day cycle time baseline (higher means slower) |
| DEGRADED_SHIFTS | Count of production shifts flagged as DEGRADED for this machine type |

**How the maintenance planner uses this:** They are already scheduling downtime for MCH-0047 (CRITICAL pump). They open this view and see: MCH-0003 (conveyor) is also CRITICAL with a concern rank of 4, and MCH-0031 (CNC lathe) is at rank 3. If those machines are in the same production area, they can bundle all three repairs into one shutdown window -- minimizing total downtime and maximizing technician utilization.

## The Data Flow Behind the Dashboard

Every view in the dashboard reads from tables that are automatically maintained by the platform:

```
View                        Data Source                              Refresh
--------------------------  ---------------------------------------  --------
Factory Floor Overview      STAGING.CROSS_MACHINE_HEALTH (DT)       5 min
Machine Detail (readings)   STAGING.SENSOR_READINGS_CLEAN (DT)      auto
Machine Detail (anomalies)  ANALYTICS.DETECTED_ANOMALIES            pipeline
Machine Detail (forecast)   ANALYTICS.FAILURE_FORECASTS              on-demand
Anomaly Feed                ANALYTICS.DETECTED_ANOMALIES            pipeline
Work Order Management       RAW.WORK_ORDERS                         pipeline
Maintenance History         RAW.MAINTENANCE_HISTORY                 static
Business Continuity         RAW.RENTAL_MACHINES + PARTS_INVENTORY   static
Cross-Machine Health        STAGING.CROSS_MACHINE_HEALTH (DT)       5 min
Cross-Machine (production)  STAGING.PERFORMANCE_BASELINE (DT)       auto
```

Dynamic tables (DT) refresh automatically. Pipeline tables are updated when the orchestration task runs (every 5 minutes when active). Static tables contain reference/historical data that changes infrequently.
